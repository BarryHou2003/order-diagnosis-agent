01 · THE PROBLEM

「只成交一单，
为什么扣了我 3000 元？」

直播电商投流的每一笔异常消耗背后，都是一个等待回答的广告主。而一次人工排查要跨多个看板取数，耗时约 30 分钟——问题每天都在发生，答案却永远供不应求。

Ⅰ · 广告主

要一个说法

投流不及预期时，最需要的是及时、专业、有数据支撑的解释。得到的却是模版回复——信任被持续消耗。

Ⅱ · 客服

有心无力

数据分散在多个看板，排查链路长；非工作时间无人响应；回复没有归因，也没有情绪安抚。

Ⅲ · 算法 & 数科

看不见全局

客诉是文本噪音，算法侧无法量化排期；数科侧分析一个 case 要手动取数、跨看板拼凑。

四方都在等同一件事：一条自动化的诊断链路。

03 · HOW IT WORKS

六层链路，一次诊断

从一句混杂着情绪的自然语言，到一份可执行的诊断报告——中间是一条严格分层的流水线。每层只做一件事，并把它做到极致。

L1

接入层 ENTRY

企微 Bot 与网页端双端接入，订单号即诊，零培训成本。

L2

意图理解 INTENT

诉求拆解 → 事实核验 → LTR 优先级排序：先听懂用户在问什么，再决定先回答什么。

L3

诊断引擎 DIAGNOSIS

成本 / 跑量 / 流速三大模块诊断规则库，显著性检验甄别真实异常与随机波动。

L4

场景路由 A–H ROUTER

A–H 场景决策，诊断与决策分离：冲突结论自动裁决，未授权动作一律过滤。

L5

报告生成 GENERATION

槽位化单 Agent 架构，运行在本地部署的 Qwen3-14B 之上——数据不出域，格式不失控。

L6

赔付闭环 SETTLEMENT

标准赔付自动判定；OCPX 未覆盖场景触发异常赔付二次判断，自动登记、全程留痕。

一条旁路：所有诊断产生的结构化诉求与数据分布，以天级监控反哺算法与数科——客诉第一次从「文本噪音」变成「可排期的工程输入」。
04 · KEY DESIGN DECISIONS

四个关键设计决策

过程中的试错与迭代不赘述——只讲最后留下来的、真正起作用的四个决策。

DECISION 01

意图识别与诉求排序

「先听懂，再回答」

规则 + 小模型分类 + BM25 正反例召回，多路信号融合后用 LTR（Learning-to-Rank）排序主诉优先级——回答顺序，就是用户体验。

为什么关键：真实客诉把现象、猜测和情绪揉成一句话。不先拆清楚「用户到底在问什么、最关心什么」，再准的诊断也答非所问。
DECISION 02

槽位化报告生成

「把自由写作，变成槽位填充」

报告被拆为固定槽位逐段生成，格式、口径、重点全部由结构约束，而非依赖模型的自由发挥。

为什么关键：数据合规要求模型本地部署、参数受限（Qwen3-14B）。我们用架构补足模型能力——在对照实验中，槽位化单 Agent 稳定胜过多 Agent 方案。
DECISION 03

诊断与决策分离

「A–H 场景路由」

先排除状态异常，再处理明确损失，最后给优化空间；冲突结论统一裁决，未授权建议自动过滤。

为什么关键：诊断可以百花齐放，决策必须口径统一。Agent 的建议一旦越界，消耗的是业务信任。
DECISION 04

三层评测体系

「每个决策，都有可复现的口径」

确定性规则 + LLM Judge + 人工复核三层评测，覆盖意图、归因、建议与表达四个维度。

为什么关键：BLEU / ROUGE 衡量不了业务正确性。没有可复现的评测口径，一切「效果更好」都只是感觉。
全部能力运行在本地部署的开源模型之上——数据不出域，成本可控： Qwen3-14B · local LTR ranking slot-based generation 3-layer evaluation

同一句客诉，两种回答

BEFORE / AFTER
BEFORE · 人工模版回复

「亲，消耗与效果受多方因素影响，建议持续优化素材与出价，如有疑问可随时联系客服。」

无归因、无数据、无赔付结论——问题被「回复」了，但没有被「回答」。

AFTER · 诊断 Agent

先回应最关心的诉求，再逐层给出数据归因 → 场景结论 → 可执行建议 → 赔付结论，全程分钟级完成，且每条诉求沉淀为结构化数据。
